# CloudKit Schema Audit — pre-Production promotion

**Date:** 2026-08-06 · **Worktree:** `cb-release-plumbing` · **Plan:** `docs/plan-2026-08-06.md` session 1A

This is the last moment the schema is freely mutable. After promotion to the Production
CloudKit environment, **every record type and field is permanent**: you can add, never
delete, never retype, never rename. See `docs/plan-2026-08-06.md` Appendix B.

**Status: D1–D9 approved by Mark 2026-08-07 and implemented.** Build green, 280 test
cases pass. Two scope additions came out of the review — see "Deferred to session 2".

Nine `@Model` types. Eight synced (`Services/AppSettings.swift:92`), one device-local.

### The good news

The schema is in better shape than expected, and two earlier decisions are paying off here:

- **Zero SwiftData relationships in the synced schema.** `BlasterScene` stores its pages as
  inline JSON `Data` rather than a `PageModel` relationship. That eliminates the entire
  class of CloudKit relationship problems — no inverses to declare, no delete rules to get
  wrong, no `.deny`.
- **Every property is optional or defaulted**, and there is no `@Attribute(.unique)`
  anywhere. Both standing house rules were followed consistently.

So this audit is about *dead weight and naming*, not about legality. That's the cheap
version of this problem.

## Findings

### F1 — `SentenceCache.audioData` is dead. Remove. ✅ high confidence

Declared `String`, only ever written as `""`, never read. Three call sites in
`SentenceCacheManager.swift:64,74,79` pass it through with a default argument. It's a
holdover from the original Blaster's `gpt-4o-audio-preview` integration; we use
`AVSpeechSynthesizer` and never receive audio from the API.

Already annotated in-code as the removal candidate for exactly this pass.

**Action:** delete the property and the three pass-through call sites.

### F2 — `TileModel.type` / the `TileType` enum are dead. Remove. ✅ high confidence

`TileType` (`.word` / `.phrase`) exists for the PRD's promoted-combo-tile feature, which
was never built. The only reference outside the model is one test asserting the default
value. (The `.type` matches in `SceneImporter` are `exportable.type` — an unrelated media
type.)

Two reasons to remove rather than keep:

1. It's a **Codable enum stored directly as an attribute**, which is the one shape the
   codebase otherwise deliberately avoids for CloudKit — `ChildProfile.interactionModeRaw`
   and `DeviceProfile.roleRaw` both store `String` + a typed accessor, with comments
   explicitly citing CloudKit compatibility. `TileModel.type` and `MetricEvent.eventType`
   are the two that didn't get the treatment. Freezing an inconsistent representation into
   the production schema is the wrong default.
2. Adding a field back later is the **permitted** direction of change. If promoted tiles
   ship in v2, `typeRaw: String` can be added then, correctly shaped.

**Action:** delete `TileType` and `TileModel.type`; update the one test.

### F3 — `MetricEvent.eventType` should be `String`-backed. ⚠️ decision needed

Same Codable-enum-as-attribute shape as F2, but `MetricEvent` is **live**: `AdminView:34,37`
computes cache hit/miss stats from it and `AdminView+LogsTab.swift:227` reads it for the
activity summary.

Normalizing to `eventTypeRaw: String` + a typed accessor makes it consistent with
`ChildProfile`/`DeviceProfile` and removes any doubt about how the field mirrors to
CloudKit. Cost: a small migration, and this is a disposable analytics stream anyway
(both `BootstrapLoader:137` and the Logs tab already delete all of it wholesale).

**Recommendation:** normalize. Low risk given the data is disposable. See also F4 — if
`MetricEvent` goes device-local, this stops mattering for the production schema entirely,
but is still worth doing for consistency.

### F4 — `MetricEvent` is the wrong side of the sync line. ⚠️ decision needed

It is by far the **highest write-volume model** — one record per cache lookup and per
cache hit, written on essentially every child interaction (`SentenceCacheManager:333`),
and bulk-generated by `BulkCacheGenerator` during scale testing (10K combinations).

Every one of those becomes a CloudKit record push. For data that is:

- disposable (wiped by bootstrap and by a Logs-tab button),
- and consumed only as **aggregate counts** on the local device.

Meanwhile `LoggedUtterance` — the record a therapist actually reviews — is a low-volume,
meaningful, genuinely cross-device history. That one clearly belongs synced.

**Recommendation: move `MetricEvent` to the `DeviceLocal` configuration.** It sheds the
sync traffic, keeps the Admin stats working exactly as they do today (they're
device-scoped statistics anyway), and removes a record type from the permanent production
schema. The one thing lost: cache-hit stats won't aggregate across a therapist's iPad and
iPhone — which is arguably more correct, since cache hit rate is a property of a device's
local cache.

This also sets the precedent for session 2's cost ledger, which should live in the same
place for the same reasons.

### F5 — `LoggedUtterance.sceneName` is write-only, and stores the wrong key. ⚠️ decision needed

Written at construction, never read anywhere in the app. Worse, it stores the scene's
**name** — but PR #44 established `sceneID` as the stable, rename-proof identity. A
caregiver renaming a scene silently orphans every historical utterance attributed to it.

Three options:

1. **Drop it.** Nothing reads it today.
2. **Replace with `sceneID`.** Keeps the intent (attributing history to a scene) and uses
   the identity the rest of the app settled on.
3. Keep both.

**Recommendation: option 2.** Utterance history attributed to a scene is a plausible
therapist-facing feature ("what did Jamie say during the Grandma's House scene?") and it's
free to store now. But store the identity that survives a rename. If it stays as a name
field and we later want the id, we're adding a second field forever and reconciling two.

### F6 — `TileArtVariant.created` is really "modified". 🔸 minor, permanent

`upsert` sets `created = .now` on an *existing* record (`TileArtVariant.swift:48`), so the
field means "last written". Nothing reads it for creation semantics today, so this is
cosmetic — but field names are frozen at promotion, and a future reader will
misinterpret it.

**Recommendation:** rename to `modified` now (a pure local rename, no data to preserve
pre-promotion). Cheap to do now, impossible to do later.

### F7 — Fields that look dead but are load-bearing. Do not touch. ✅

Recording these so a future pass doesn't "clean them up":

- `SentenceCache.created` — the tie-breaker in
  `CloudKitDedupReconciler.dedupeSentenceCache` when two synced duplicates share a
  `hitCount`. Already annotated in-code.
- `ChildProfile.notes` — has no UI, but `CloudKitDedupReconciler:186` matches on the
  `"Seeded from prior install"` prefix to identify migration-seeded profiles. Removing it
  breaks dedup. (Worth a follow-up: using a free-text notes field as a marker channel is
  fragile. Not a schema problem — leave for later.)
- `BlasterScene.receivedLabel`, `sourceURL`, `creationSummary` — all read by the scenes
  UI (provenance line, import attribution, post-creation summary).
- `SentenceCache.isPinned` — 16 references; drives eviction immunity.

### F8 — `ChildProfile.ttsRate` is `Float`. 🔸 note only

The only non-`String`/`Int`/`Bool`/`Date`/`Data` scalar in the schema (`ttsVolume` too).
`Float` mirrors to CloudKit's Double fine. No action — recording it so the type inventory
is complete.

### D5, revised during review

The original recommendation was to *replace* `sceneName` with `sceneID`. Mark raised scene
**deletion**: a stable id is useless once the scene it points at is gone.

That's correct, and it changes the answer to **store both** — the standard analytics shape:

- `sceneID` — identity. Survives a rename; use it to join or filter history to a scene.
- `sceneName` — a display *snapshot* taken at commit time. Survives deletion.

`LoggedUtterance.sceneDisplayName(resolving:)` implements the fallback ladder: live scene's
current name → the snapshot → nil (caller omits attribution rather than rendering a
dangling id). So a rename is reflected in history, and a deletion still reads correctly.

Two permanent fields instead of one, which is the right trade — the alternative is
discovering later that we need the other one and adding it anyway.

### D9 note

Removing the legacy raws is a **zero-behavior-change** edit: `fromRawValue`'s `default:`
branch already returned `.caregiver` for them. The two migration tests were reframed from
"`personal` migrates" / "`therapist` migrates" into a parameterized test of the invariant
that actually matters going forward — *any* unrecognized role resolves to `.caregiver` —
plus a new test that `patient` is **not** absorbed by the default branch, which is the case
worth protecting.

## Deferred to session 2 (from Mark's review)

Both additions are about **local telemetry streams**, and both land naturally alongside
session 2's cost ledger, which is a third stream with identical needs. Building the
surface once for all three beats building it twice.

Critically, none of this is promotion-blocked: `MetricEvent` is now device-local (D3) and
the cost ledger will be too (D7), so **their schemas stay freely mutable forever**. That's
what makes deferring safe.

### S2-A — Storage visibility

Show what these streams actually consume, on the relevant admin pages. Real numbers are
available: the SwiftData store files can be stat'ed on disk, per-model record counts are
exact fetches, and `TileArtVariant`'s `.externalStorage` blobs live in an external-data
directory that can be sized. Art is expected to dominate by a wide margin.

### S2-B — Bounded growth with compaction, not deletion

Mark's framing: rather than throwing old metrics away, fold a time range of them into a
single aggregated row — so after 6–12 months the oldest history collapses instead of
vanishing.

**Schema groundwork landed now** so the later feature is purely additive:

- `MetricEvent.count: Int = 1` — occurrences this row represents.
- `MetricEvent.periodEnd: Date?` — end of the covered range; nil for a live event.
- `MetricEvent.isAggregate` — computed.
- **`AdminView.metricTotal(subjectType:eventType:)` now sums `count` instead of counting
  rows.** This is the part that had to happen now: had compaction shipped against
  row-counting readers, every stat would have silently under-reported. The old
  `.count { }` call sites are gone.

Still to build in session 2: the compaction pass itself (group by subject + event type +
period, collapse, stamp `periodEnd`), the retention settings UI, and the choice of default
window. `AdminView+LogsTab.flushAllCache` deletes rows directly and is unaffected.

## Remaining session-1 work

- **1B — ✅ done.** `BlasterSchemaV1: VersionedSchema` + `BlasterMigrationPlan`
  (`Models/SchemaVersions.swift`), wired into both container paths in
  `AppSettings.setModelContainer`. The version owns the **synced/local partition**
  (`syncedModels` / `localModels`), and `AppSettings` builds its configurations from
  those lists — so the configurations and the schema version cannot drift apart.
  `SchemaVersionTests` (7 cases) pins the exact membership of each partition, asserts they
  are disjoint and that `models` is their union, and opens a real container at V1 through
  the migration plan, round-tripping a model from each side.

  The membership tests are deliberately literal: adding a model to the synced set should
  *fail a test*, because that's the moment to ask whether it really needs to sync and
  whether it's shaped for a schema it can never remove a field from.

- **1C** — reset the Development CloudKit environment, let SwiftData regenerate a clean
  schema from the audited models, review it record-type-by-record-type in the Console,
  then **Deploy Schema to Production**.
- **1D** — verify against Production (Ad Hoc export loop; see plan Appendix A).
- **1E** — `PrivacyInfo.xcprivacy`, `ITSAppUsesNonExemptEncryption`, version numbers.

### Device sequencing for 1C (agreed 2026-08-09)

In the **Development** environment, SwiftData auto-creates record types and fields on
demand but never removes them. Two consequences:

1. Running the post-audit build against the *current* dev schema would layer the new fields
   on top of the cruft this audit removed. Harmless (the reset wipes it) but pointless —
   hence no device runs before the reset.
2. **The real hazard is the reverse:** after the reset, any device still on an *older*
   build that touches CloudKit will re-create the dead fields in the freshly-clean schema.
   If that happens before promotion, the cruft becomes permanent.

So the gate is: **once dev is reset, every device must be on the post-reset build before
any of them syncs.** All schema-affecting code (1A, 1B) lands first; the reset, review, and
promotion happen as a single ceremony. The reset also wipes dev *data*, so it's the
factory-reset-and-re-add-packs drill.
