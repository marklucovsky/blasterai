## Session 1 — `cb-release-plumbing` — ✅ COMPLETE except promotion (2026-08-11)

**Goal:** a schema we are willing to live with forever, deployed to CloudKit Production,
in a build that can be submitted.

This is the only irreversible session. **A CloudKit Production schema is
additive-only forever** — see Appendix B. Everything else on this list can be redone.

### Outcome

Shipped as **PR #50** (schema audit D1–D9, `BlasterSchemaV1` + migration plan, privacy
manifest, export compliance, 0.9.0), plus **PR #51** for what acceptance testing then
found. 296 test cases pass.

**Promotion (Phases 4–5) is deliberately deferred to session 4**, immediately before the
first TestFlight build. See the deferral note in `docs/cloudkit-promotion-runbook.md`.
Phases 0–3 have been run and pass.

Running the ceremony as far as Phase 3 is what justified the deferral. It surfaced four
problems, none of which code review had caught:

1. **`TileModel.retiredReason` was absent from the schema.** CloudKit stores no nulls, so
   a nil optional is never written and its field never materializes — and the Production
   schema is read-only, so it would never have existed. Forced the **no-optional-stored-
   properties rule** now recorded on `BlasterSchemaV1`; six fields converted.
2. **`RecordedScript.sceneName` held an identifier, not a name.** Renamed to `sceneRef`
   before a misleading field name could be frozen forever.
3. **Two-device install destroyed a caregiver's scene edit.** Every fresh install
   bootstraps its own system scenes (the seed flag is per-device and never syncs), and
   the reconciler collapsed them by key — where a fresh bootstrap always looks *newer*
   than real work. Fixed by making system scenes **immutable**, with edits going to a
   clone; the set of scenes that can be collapsed is now exactly the set that can never
   diverge. All Tiles removed in the same pass.
4. **Pack pages committed a single tile** — the commit path filtered against a tile
   lookup captured before the pack installed its words.

Two of those would have been permanent had we promoted on the first pass. The lesson is
recorded here because it generalizes: **the value of the ceremony is the review, and the
review only works against a schema that is still mutable.**

### 1A. Schema audit

Nine `@Model` types. Eight are in the synced schema (`Services/AppSettings.swift:92`),
one is device-local (`DeviceProfile`, `cloudKitDatabase: .none`).

Synced: `TileModel`, `TileArtVariant`, `SentenceCache`, `BlasterScene`, `MetricEvent`,
`RecordedScript`, `LoggedUtterance`, `ChildProfile`.

For each model, for each property:

- **Dead?** `SentenceCache.audioData` is confirmed dead (we use `AVSpeechSynthesizer`,
  not returned audio). `SentenceCache.created` is load-bearing for dedup — keep. Sweep
  for others; a property that is written but never read still costs a permanent
  production field.
- **CloudKit-legal?** Every property optional or defaulted; every relationship optional
  with an inverse; no `@Attribute(.unique)` (already our standing rule); no `.deny`
  delete rules. Violations surface as a container-init failure only in some
  configurations — assert them in a test instead.
- **Named right?** Field names are permanent after promotion. `originalName:` can
  rename the *Swift* property later, but the CloudKit field keeps its old name forever.
  Fix regrettable names now.
- **Typed right?** Type changes after promotion require a new field and a migration.
  Especially check the String-backed enums (`ChildProfile.interactionMode`,
  `DeviceProfile` role, `TileModel.retiredReason`) — String is the right call for
  CloudKit, just confirm every one is consistent.
- **Right side of the sync line?** Anything device-scoped belongs in the `DeviceLocal`
  config, not the synced one. `MetricEvent` and `RecordedScript` are worth re-examining
  here.

Also decide, now: **where does the cost/token ledger live?** It is built in session 2,
but if it is a synced model it must exist before promotion. Recommendation: **device-local**
— cost is per-device/per-API-key, not per-child, and keeping it out of the synced schema
means session 2 cannot destabilize a promoted schema. Decide explicitly and record it.

Deliverable: `docs/schema-audit-2026-08-XX.md` — final field inventory + rationale, and
the change-rules section from Appendix B restated as house rules.

### 1B. Versioned schema

Introduce `SchemaV1: VersionedSchema` and a `SchemaMigrationPlan` now, while there is
exactly one version and the migration plan is empty. Retrofitting this after a pilot has
real user data is materially harder. Add a test that opens a container at V1.

### 1C. Reset dev, then promote

The dev CloudKit schema has accumulated every field that ever existed during
development — including ones we deleted from the Swift models. Promoting as-is makes all
of that cruft permanent.

Order matters:

1. Land the audited models (1A/1B).
2. **CloudKit Console → Reset Development Environment.** This wipes dev schema + dev data.
   Production has no schema yet, so nothing is copied down. This is the one moment we can
   get a clean slate.
3. Run the app fresh on a device with iCloud on → SwiftData recreates the dev schema from
   the audited models only.
4. Inspect the regenerated dev schema in the Console record-type-by-record-type. This is
   the last review before permanence.
5. **Deploy Schema to Production.**

Note the existing wipe semantics rule (`project_cloudkit_wipe_semantics`): app-level reset
is a *local* wipe that preserves cloud data. The CloudKit Console dev reset is a different,
deliberate operation — it is fine here only because we're pre-pilot and dev data is
disposable. Do not repeat it once testers have data.

### 1D. Production verification loop

See Appendix A. Establish and **document** the loop before promoting, so step 5 above can
be verified same-day.

### 1E. Submission plumbing

- `PrivacyInfo.xcprivacy` — required-reason API declarations. Audit actual usage; at
  minimum `NSPrivacyAccessedAPICategoryUserDefaults` (reason `CA92.1`), plus file
  timestamp / disk space / system boot time if any dependency touches them. Data
  collection: **none** — no tracking, no analytics SDK, no third-party SDKs. This is a
  genuinely strong privacy manifest and is worth a line in the marketing copy.
- `ITSAppUsesNonExemptEncryption = false` in Info.plist (HTTPS-only ⇒ exempt). Without
  it, every single build prompts for export compliance in App Store Connect.
- `MARKETING_VERSION` → decide `0.9.0` (pilot honesty) vs `1.0.0`. `CURRENT_PROJECT_VERSION`
  → an incrementing build number scheme.
- Confirm the `remote-notification` background mode and `aps-environment` are actually
  needed (CloudKit push) and correctly configured for a distribution build.
- App icon: currently a single `AppIcon.png`. Confirm it satisfies iOS 26 + Mac
  (Designed for iPad) requirements.

### Exit criteria

- Schema audit doc committed; models match it.
- `SchemaV1` + migration plan in place, test green.
- Dev environment reset, schema regenerated clean, **deployed to Production**.
- A Production-environment build verified on ≥2 devices syncing real data.
- Privacy manifest + export compliance + version numbers landed.
- Full test suite green.

### 2A. Token & cost accounting (the bigger half)

Every OpenAI endpoint we consume today:

| Service | Endpoint | Notes |
|---|---|---|
| `OpenAISentenceProvider` | `/v1/chat/completions` | the hot path; cache-gated |
| `SceneGeneratorService` | `/v1/chat/completions` | caregiver-triggered, large prompts |
| `SceneRefinerService` | `/v1/chat/completions` | iterative, can be called repeatedly |
| `PageGeneratorService` | `/v1/chat/completions` (×2 call sites) | |
| `TileSuggestionService` | `/v1/chat/completions` | |
| `WordModerationService` | `/v1/chat/completions` | the age-appropriateness rubric |
| `WordModerationService` | `/v1/moderations` | free |
| `TileImageGenerator` | `/v1/images/generations`, `/v1/images/edits` | **almost certainly the dominant cost** |
| `OpenAIKeyValidator` | `/v1/models` | free |

Work:

1. **Capture** — every call site returns `usage` (prompt/completion/total, plus cached
   input tokens where the model reports them). Route all of them through one recording
   seam rather than nine ad-hoc call sites. Image endpoints bill per image/size, not
   tokens — record count + size + model instead.
2. **Price** — a single editable price table keyed by model id. Look up current pricing
   at implementation time; do not hardcode numbers from memory. Include cached-input
   discount rates. Make it obvious the table is a snapshot with a date.
3. **Store** — device-local ledger (per the session-1 decision), with enough granularity
   to answer "what did this child cost this month" and "what did scene generation cost me".
4. **Surface** — Admin → Logs. Two audiences:
   - *Caregiver:* "This month: $0.14. 312 sentences, 268 served from cache (86%)."
   - *Us:* per-endpoint breakdown, cache hit rate, cost-per-utterance trend.
5. **Prove the claim** — the GTM doc asserts ~$0.10–0.50/month with gpt-4o-mini. Run a
   real week on a real device and either confirm the number or fix the claim
   (`docs/gtm.md`, the site, the deck — same discipline as `docs/claims-audit-2026-07-20.md`).

The interesting result to look for: **art generation likely dwarfs sentence generation**,
which means the honest claim may be "pennies a month to talk; a one-time cost when a
caregiver builds a new scene." That's still a devastating comparison to $300/yr, and it's
true.

### 2B. Bundle slim

- Current: p3d 140 MB + classic 74 MB + hc 62 MB = 276 MB, plus a 19 MB asset catalog.

## Appendix A — How to test CloudKit Production

**The rule:** the CloudKit environment is chosen by *how the app was signed and installed*,
not by anything in our code.

- Built and run from Xcode (development signing) → **Development** environment. Always.
  There is no "use production" switch in the running app.
- Distributed via TestFlight or the App Store → **Production**.
- Exported as an **Ad Hoc** (or Enterprise) archive and installed on a registered device →
  **Production**. This is the loop worth having: it skips App Store Connect upload and
  processing entirely, so the turnaround is minutes and purely local.

So Mark's Tibls experience is right — TestFlight is the standard answer — but Ad Hoc export
is a faster inner loop for the same environment, and it's worth setting up in session 1:

1. Archive with the Release configuration.
2. Distribute → Ad Hoc (device must be in the provisioning profile).
3. Install via Xcode's Devices & Simulators window or Apple Configurator.
4. That build talks to Production CloudKit.

There is also an entitlement, `com.apple.developer.icloud-container-environment`
(`Development` / `Production`), that Xcode writes into archived builds' entitlements. Whether
automatic signing will produce a *development-installable* build carrying `Production` is
worth a 20-minute spike in session 1 — if it works, we get production CloudKit on a plain
build-and-run, which is the fastest possible loop. If automatic signing refuses (profile
doesn't include the entitlement), fall back to Ad Hoc. **Do not block session 1 on this
spike; Ad Hoc is sufficient.**

Whatever works, document it in the schema-audit doc as the standing procedure, along with:

- CloudKit Console → Production database, for inspecting what actually landed.
- The two-device sync check (already exercised for PR #49) run against Production.
- A note that a Production sync bug found *after* testers have data is much more expensive
  than one found now — hence verifying immediately after promotion, not at session 4.

## Appendix B — CloudKit schema rules, forever

Once a schema is deployed to Production, these become permanent constraints. This is the
"solid footing" Mark asked for — the point is not to be perfect, it's to know exactly what
we can and cannot change later.

**You can, safely, at any time:**

- Add a new record type (new `@Model`).
- Add a new field to an existing record type (new property) — must be optional or defaulted.
- Add indexes.
- Stop writing a field.

**You can never, in Production:**

- Delete a record type or a field. They persist in the schema forever. Removing a property
  from the Swift model is fine locally, but the CloudKit field stays.
- Change a field's type. A `String` that should have been an `Int` is a `String` forever;
  the fix is a new field plus migration code that carries the old values over.
- Rename a field. `originalName:` renames the Swift property while keeping the CloudKit
  field name — the on-disk name is what's frozen.
- Make an existing field required.

**Therefore, before promotion:** names and types matter far more than they normally do,
and dead fields are permanent dead weight. After promotion, every schema change is
additive and every migration must be written to bridge old → new, with old readers still
in the field (a tester on build 3 must not be broken by build 7's schema).

**Ongoing house rules:**

- Every new property: optional or defaulted. No exceptions.
- No `@Attribute(.unique)` anywhere — dedup in code (this is already our practice:
  `BootstrapLoader`, `ProfileMigration`, `CloudKitDedupReconciler`).
- Every relationship optional, with an inverse, and never `.deny`.
- Bump `SchemaVX` and add a migration stage for any change beyond a pure additive field.
- Device-scoped data goes in the `DeviceLocal` configuration, never the synced one.

## Appendix C — Mac (Designed for iPad) test plan

The app is SwiftUI + iPad-first, so running on Apple Silicon Macs is nearly free, and the
extra canvas plausibly makes scene editing and vocabulary management genuinely better for
therapists — the exact surface a pilot is meant to evaluate.

**Enabling it:**

1. Xcode target → Supported Destinations → add **Mac (Designed for iPad)**.
2. Build and run to "My Mac (Designed for iPad)" — no TestFlight needed for the dev loop.
3. For distribution: App Store Connect → the iOS app's availability must have Mac enabled.
   Testers on macOS then see the app in **TestFlight for Mac**.

**What to test specifically** (these are the known breakage classes, not a generic sweep):

- **AdminGate.** Face ID doesn't exist on Mac; Touch ID may or may not be present. The PIN
  path has to be complete and discoverable, and biometric failure must degrade gracefully
  rather than lock a caregiver out. This is the single highest-risk item.
- **Long-press gestures.** The caregiver menu (long-press Home) and the tile note-capture
  long-press map to click-and-hold. Verify both are actually reachable with a trackpad.
- **Window resizing.** Verify the grid's `tilesPerPage(geo:isLandscape:)` math and the
  portrait snap-offset `VStack` behave across arbitrary window sizes, not just device
  aspect ratios.
- **Keyboard and pointer.** Hand-typed sentences, CSV bulk add, scene names, PIN entry —
  all currently assume the iPad software keyboard. `NumericKeypad` exists specifically to
  bypass the iPad system keyboard; check it isn't hostile with a hardware keyboard.
- **Speech.** `AVSpeechSynthesizer` voices differ on macOS; the premium/enhanced voice
  download story is different. Verify the voice picker doesn't offer voices that don't exist.
- **File import / share.** `.blasterscene` document type registration, `fileImporter`, and
  AirDrop behave differently on Mac.
- **CloudKit.** Mac + iPad + iPhone three-way sync against Production is the real test.

**Scope decision to make in session 3:** is Mac a *supported pilot platform* (screenshots,
tester instructions, bug triage) or a *known-works-but-unsupported* bonus? Recommendation:
supported for caregivers, not advertised for the child surface — a child using a Mac as an
AAC device is not the use case, but a therapist building scenes on one absolutely is.
